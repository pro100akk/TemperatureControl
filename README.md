# Apartment Comfort 0.1.0

Пользовательская интеграция Home Assistant для одной температурной зоны квартиры. Первая экспериментальная версия: UI-настройка, пять **существующих** периодов дня, батарея с обдувом, резервный пол, кондиционер и рекомендации по проветриванию.

**На реальном Home Assistant эта версия пока не проверялась.** Локально проверены модель управления и адаптер команд с имитацией границы HA. Начните с режима наблюдения, включённого по умолчанию. Управление физическими приборами в рамках разработки не включалось.

[Обновлённый план и следующие этапы](docs/PLAN.md).

Исходный проект: **TemperatureControl**. Лицензия: [MIT](LICENSE). Репозиторий на этапе разработки должен оставаться закрытым; перевод в публичный доступ выполняется отдельно по решению владельца.

## Установка

### Через HACS / GitHub

После публикации проекта в публичном GitHub-репозитории:

1. Откройте **HACS → ⋮ → Пользовательские репозитории (Custom repositories)**.
2. Вставьте URL репозитория проекта и выберите тип **Интеграция (Integration)**.
3. Добавьте репозиторий, найдите **Apartment Comfort** и скачайте его.
4. Перезапустите Home Assistant.
5. Откройте **Настройки → Устройства и службы → Добавить интеграцию → Apartment Comfort** и настройте датчики и периоды.

HACS загружает файлы интеграции из `custom_components/apartment_comfort`. Саму интеграцию после скачивания необходимо добавить в HA отдельно. Если она уже настроена вручную, повторно добавлять её не нужно: HACS будет управлять файлами того же домена.

Для обновлений публикуются GitHub Releases с тегами, совпадающими с версией в `manifest.json` (`v0.1.0` для первой версии). Пока релизов нет, используется основная ветка. ZIP из `dist/` предназначен для ручной установки; HACS получает исходники репозитория, опция `zip_release` не включена.

**Репозиторий:** [pro100akk/TemperatureControl](https://github.com/pro100akk/TemperatureControl), видимость **Private**. Пока репозиторий приватный, установка через HACS недоступна — используйте ручную установку. После отдельного решения открыть проект будет доступна схема HACS выше. [Порядок публикации](docs/HACS.md).

Официальные инструкции: [пользовательские репозитории HACS](https://hacs.dev/docs/faq/custom_repositories/), [требования к интеграции](https://www.hacs.dev/docs/publish/integration/).

### Ручная установка

1. Скопируйте каталог `custom_components/apartment_comfort` в `/config/custom_components/` вашего Home Assistant. Либо распакуйте архив из `dist/` так, чтобы получился `/config/custom_components/apartment_comfort/manifest.json`.
2. Перезапустите Home Assistant.
3. Откройте **Настройки → Устройства и службы → Добавить интеграцию → Apartment Comfort**.
4. Выберите основной температурный датчик и существующую сущность периода дня (`input_select`, `select` или `sensor`). Добавьте остальные датчики по необходимости.
5. Выберите приборы. Укажите **точные состояния** пяти периодов из «Инструменты разработчика → Состояния» и температуры для них. Отображаемая русская подпись может отличаться от исходного состояния.
6. Оставьте «Управлять приборами» выключенным и проверьте рекомендации и атрибут `decision` сенсора состояния.
7. Для передачи управления выключите выбранные приборы, отключите конфликтующие температурные автоматизации, затем включите управление в **Настроить**. Каждая роль оборудования назначается только одной зоне интеграции.

Ориентир API — HA 2025.12 и новее; реальная совместимость конкретной версии HA пока не подтверждена. Используется `probatio` при наличии, иначе `voluptuous`, предоставляемые HA. Сторонние Python-библиотеки не нужны.

## Сущности, которые создаются

- **Термостат**: режимы heat/cool/off, текущая и целевая температура, текущая влажность. Нагрев и охлаждение выбираются вручную; автоматического сезонного режима пока нет.
- **Состояние контроллера**: наблюдение, ручная пауза, ожидание, нагрев батареей, резерв, охлаждение, проветривание, блокировка. Атрибуты показывают запрошенное решение, входные данные и проблемы.
- **Рекомендация по проветриванию**: открыть, продолжить, закрыть, проверить датчик/качество воздуха. Атрибуты `reasons` и `exhaust_recommendations` объясняют причины.
- **Действующая целевая температура**: отдельный сенсор для графиков.

Русский и английский интерфейсы включены. Идентификаторы сущностей назначает HA; найдите их на странице устройства интеграции. Диагностику можно скачать с карточки интеграции.

`hvac_action` термостата показывает только сообщённое подконтрольными приборами heating/cooling, а не просто факт отправки команды. Если прибор не предоставляет `hvac_action`, активная работа не заявляется. План контроллера доступен отдельно в `planned_action` и `decision`.

## Периоды и ручная температура

Утро, день, вечер, подготовка к ночи и ночь привязываются к произвольным точным строкам вашей сущности. Переходы по будильнику и ручной команде остаются в существующих автоматизациях. Начальные температуры: 22 / 22 / 22 / 21 / 20,5 °C.

Изменение температуры на виртуальном термостате задаёт временную уставку до следующего изменения периода. Профиль `schedule` немедленно возвращает текущую уставку периода. При неизвестном периоде и отсутствии ручной уставки управление блокируется.

## Управление и ограничения v0.1

| Прибор/данные | Поддержка |
|---|---|
| Термоголовка | `climate` с `heat`, `off`, `set_temperature`; гистерезис по основному датчику |
| Вентиляторы батареи | `fan.set_percentage`; требуется датчик температуры поверхности батареи |
| Пол | Только `climate` со штатным термостатом, режимы `heat`/`off` |
| Кондиционер | `climate` с `cool`/`off`; минимум 5 минут выключенного состояния, настраивается |
| Окно | `binary_sensor`/`input_boolean`, `on` означает открыто |
| Работа центрального отопления | `on` означает доступно; `off` — подтверждённо недоступно |
| CO₂ | Числовой `sensor`, единица `ppm` |
| Влажность | Числовой `sensor`, единица `%` |
| Готовка | Бинарный признак `on`/`off`; от числового датчика мощности нужен отдельный шаблон |
| Присутствие, температура трубы, мощность ПК, состояния вытяжек | Подключение и показ в диагностических атрибутах; без влияния на тепловые коэффициенты |
| Вытяжки | Рекомендации включения; никаких автоматических команд |

Термоголовка получает комнатную целевую уставку. Встроенный датчик головки остаётся частью её собственного регулирования. Если возле батареи существенно теплее, помещение может недогреваться; адаптер внешнего датчика/клапана или обучаемая коррекция ещё не реализованы. Здесь нет PI/PID, прогноза и самообучения.

Батарея всегда имеет приоритет, денежная экономия её тепла не учитывается. Пол по умолчанию запрещён. При разрешении он включается только после устойчивого дефицита и подтверждённой недоступности батареи (либо если батарея вообще не настроена). Недостаточная мощность работающей батареи автоматически аварией не объявляется. Лимит непрерывного запроса пола сохраняется при перезапуске; после превышения резерв блокируется до достижения целевой температуры. Это не суточный бюджет энергии и не замена аппаратной защите пола.

Температура трубы сама по себе не объявляет аварию: участок после закрытого клапана может остывать штатно. Используется выбранный внешний признак доступности отопления. Неизвестный признак не запускает резерв автоматически.

Обдув включается при температуре поверхности батареи выше комнатной более чем на 2 °C. Во время подготовки ко сну и ночью применяется отдельный предел скорости. При отсутствии датчика поверхности автоматического обдува нет.

Открытие окна сразу приостанавливает подконтрольный нагрев и кондиционер. Закрытие возвращает обычную логику; дополнительной выдержки закрытия в v0.1 нет. Неизвестное состояние настроенного датчика окна блокирует управление. Если датчик окна не задан, предполагается закрытое окно.

Прибор, уже включённый внешним управлением, не захватывается. Перед передачей управления выключите его. Противоположный источник должен сообщить `off`, прежде чем разрешится нагрев/охлаждение. Успешный вызов службы не считается подтверждением остановки.

Ручное изменение физического прибора через UI HA с прямым пользовательским контекстом ставит контроллер на паузу и отдаёт этот прибор пользователю. Возобновление — профиль `schedule` или выбор режима на виртуальном термостате. Изменения физической кнопкой, облаком и чужими автоматизациями не всегда имеют распознаваемый контекст: **одновременные конкурирующие автоматизации не поддерживаются**. В ручной паузе интеграция не осуществляет защитное регулирование; действуют штатные регуляторы приборов.

При отключении виртуального термостата, потере главного датчика и выгрузке интеграции останавливаются только приборы, взятые ею под управление. Если остановка не подтверждена, сохраняется владение, показывается проблема и выгрузка не подтверждается. После остановки самого HA никакой программный контроль недоступен; локальные термостаты приборов должны быть исправны.

## Качество воздуха

Начальные настраиваемые пороги: CO₂ 1000/800 ppm, влажность квартиры 65/58 %, душа 70/62 %. Это стартовые параметры автоматизации, а не медицинские или нормативные границы.

- CO₂, готовка и перегрев при прохладной улице могут рекомендовать открыть окно.
- Влажность душа рекомендует вытяжку; в v0.1 используется порог, а не скорость роста влажности.
- Для осушения квартиры сравнивается абсолютная влажность. Нужны температура и влажность улицы. Без них рекомендация сообщает неопределённость; высокая относительная влажность улицы зимой сама по себе не запрещает проветривание.
- Если помещение остыло, рекомендация закрыть окно явно сохраняет сведения о нерешённой проблеме воздуха.
- Если причины исчезли, а данные о CO₂/готовке неизвестны или отсутствуют, вместо уверенной команды закрыть окно предлагается проверить воздух.
- Измерение CO₂ не обнаруживает все загрязнения при готовке. Нужен отдельный признак готовки.

Коды `reasons`: `co2`, `humidity`, `cooking`, `free_cooling`.
Коды `exhaust_recommendations`: `shower_exhaust`, `kitchen_exhaust`, `humidity_check_outdoor_air`, `humidity_outdoors_not_drier`.

Никакие уведомления автоматически не отправляются. Рекомендация видна на карточке сущности; её можно использовать в своей автоматизации уведомлений с задержкой и ночными ограничениями. Окно никогда не открывается автоматически.

## Проверки и разработка

```text
python -m unittest discover -s tests -v
python -m compileall -q custom_components tools tests
python tools/build_assets.py
```

Тесты модели проверяют периоды, аварийный резерв, гистерезис, окно, обдув, CO₂ и влажность. Тесты адаптера используют имитацию HA: команды, подтверждение остановки, блокировку конкурирующих режимов, единицы измерения, потерю датчика, сохранение лимита пола и ручную уставку. Они не запускают настоящий HA и не проверяют его загрузчик, интерфейс настройки или реальные драйверы приборов.

Переводы генерируются из `tools/build_assets.py`; скрипт также создаёт архив без тестов и кэшей. Исходники, README и план доступны для доработки. Для следующего этапа нужны версия HA и реальные возможности/атрибуты термоголовки, пола, кондиционера и вентилятора.
